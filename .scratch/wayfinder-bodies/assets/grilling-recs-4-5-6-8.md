## #4 Baseline Config A
Recommendation: Use **OpenCode** as the primary scored Config A, pinned to the same model, provider, temperature, context window, tool permissions, and wall-clock/token budget as CLAI. Put **Pi** in the appendix as the strongest lightweight secondary comparison, and treat Codex CLI and Cursor CLI as informal only unless they can expose and honor the same model and budget controls.
Rationale: OpenCode is the most defensible model-independent, terminal-native baseline among the candidates and is close enough in tool-loop capability to isolate the harness delta without requiring a fork. Pi is valuable corroboration, while product-controlled model routing or opaque accounting in Codex/Cursor can turn the headline result into a model-or-budget comparison.
First grill question: If OpenCode cannot report token/tool-call usage in the same accounting units as CLAI, should Config A switch to Pi or should the study enforce a wall-clock plus provider-reported token cap externally?

## #5 Task-graph shape
Recommendation: Ship a small explicit DAG: `intake → plan → (repo discovery || verification discovery) → merge checkpoint → implement → verify → finish`, with exactly one failure edge from `verify → diagnose/repair → reverify`, then stop and report failure if the second verification fails. Use one coordinator/executor and allow the two read-only discovery nodes to run as narrow specialists; do not create additional implementation agents for the MVP.
Rationale: This demonstrates real parallelism, role boundaries, checkpoints, early stopping, and dynamic replanning while keeping ownership of edits coherent. Persist node status, inputs/outputs, dependencies, and the recovery edge in JSONL so the same graph is directly renderable in the reviewer trace.
First grill question: Must item 15 prove separate model-agent identities, or is a typed task DAG executed by one coordinator with parallel read-only workers sufficient?

## #6 Verification-first contract
Recommendation: A run may finish successfully only when every required command in a task/repo-derived verification manifest exits zero—normally targeted tests first, then lint, typecheck, build, and broader tests as applicable—and the final opaque evaluator hook also passes. Record each command, exit code, duration, output digest, git revision/diff digest, and resulting supersedable `evidence` memory row in JSONL/OTel; on the injected failure, create one repair node from the observed diagnostics, rerun the failed check, then rerun the full required manifest, with no second recovery loop.
Rationale: A manifest keeps the contract portable across fixture repositories and Terminal-Bench-style tasks while making completion a deterministic verifier decision rather than model confidence. The one bounded recovery path proves evidence-driven replanning without allowing endless test-fix loops or stale evidence to authorize completion.
First grill question: Should the hidden evaluator return actionable diagnostics for the single recovery attempt, or expose only pass/fail to preserve evaluator secrecy?

## #8 Threat model / approval policy
Recommendation: Default-deny capabilities outside the participant-controlled repository: run tools inside `@anthropic-ai/sandbox-runtime`, mount only the workspace and explicit scratch paths, scrub inherited environment variables, disable host process access, and deny network after setup. Require an explicit, trace-recorded approval for allowlisted dependency-install network access, secret injection, writes outside the repo, or destructive commands; never permit known secret reads/exfiltration, provide immediate process-tree kill plus sandbox teardown, and demo a repository prompt-injection requesting an environment-secret upload being blocked without approval.
Rationale: This draws a simple enforceable boundary around the two realistic risks—untrusted repository instructions and tool escape—while producing concrete governance evidence through policy decisions, approvals, denials, and kill events in JSONL/OTel. Separating a narrow setup-network phase from the agent phase avoids making ordinary package installation impossible without leaving general egress available to compromised code.
First grill question: Do any scored tasks require network access during execution rather than setup, forcing a per-domain egress allowlist instead of a hard post-setup network cutoff?
